# Authentication and authorization

LiteGym uses cookie-based session authentication backed by a custom HMAC-signed token generated in the Go backend.

## Main files

- `backend/internal/service/token_service.go`
- `backend/internal/transport/handlers/auth_handler.go`
- `backend/internal/transport/middleware/auth_middleware.go`
- `frontend/src/components/AuthenticatedLayoutRoute.tsx`

## Authentication model

The application does not currently rely on an external identity provider. Instead, it uses:

- backend-managed login
- a signed token generated by the backend
- an `HttpOnly` cookie stored in the browser

## Login flow

1. frontend submits `POST /api/auth/login`
2. backend authenticates credentials through `UserService`
3. backend generates a signed token with user claims
4. backend sets the auth cookie
5. frontend receives the user payload and continues into the protected app

## Token format

The token is JWT-like in shape, but implemented manually in the project rather than via a JWT library.

Token structure:

- header
- claims payload
- HMAC SHA-256 signature

Important claims:

- `sub`
- `email`
- `username`
- `role`
- `iss`
- `iat`
- `exp`

## Cookie behavior

The auth cookie is configured in `AuthHandler.Login` with:

- `HttpOnly = true`
- `SameSite = Lax`
- `Path = /`
- `Secure` controlled by config
- `MaxAge` derived from token TTL

This means:

- JavaScript in the browser cannot directly read the token
- requests must include credentials for authenticated fetches

## Session validation

Protected routes pass through `AuthMiddleware.RequireAuth()`.

Validation steps:

1. read the configured auth cookie
2. parse and verify the token signature
3. verify token expiration
4. optionally verify that the referenced user still exists in the database
5. inject claims into Gin context

Context values currently stored:

- `user_id`
- `user_email`
- `username`
- `user_role`

## Stale token handling

The middleware now protects against a subtle but important problem:

- a token can still be cryptographically valid even if the underlying user row no longer exists

To avoid that inconsistency, the middleware uses `UserService.GetByID(...)` when available. If the user does not exist, the request is rejected with `401`.

## Authorization model

The project currently uses a lightweight role model:

- `user`
- `admin`

Role information is included in the token claims and made available to handlers through the request context.

Examples of authorization-sensitive behavior:

- admin-specific frontend navigation
- official exercise creation/update restrictions

## Frontend session checks

The frontend protected shell is implemented in:

- `frontend/src/components/AuthenticatedLayoutRoute.tsx`

It requests:

- `GET /api/auth/me`

If the request fails, the user is redirected back to the login route.

## Logout flow

`POST /api/auth/logout` clears the auth cookie by setting an expired cookie with the same name and path.

## Operational notes

- fetch calls to authenticated endpoints must use `credentials: "include"`
- cookie name is configurable through `AUTH_COOKIE_NAME`
- secure-cookie behavior is configurable through `AUTH_COOKIE_SECURE`
- token lifetime is configurable through `AUTH_TOKEN_TTL`
